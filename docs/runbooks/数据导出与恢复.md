# 数据导出与恢复 Runbook

> 对应里程碑：[`M6 数据主权与生命周期`](../roadmap.md#m6-数据主权与生命周期)
>
> 适用版本：CloudMind 数据包格式 v2

## 数据包内容

每个导出目录包含：

- `manifest.json`：格式版本、D1 表行数、R2 key、Vectorize 索引要求和逐文件 SHA-256。
- `database/tables/*.ndjson`：D1 业务表的完整数据；FTS 属于可重建索引，不重复导出。
- `r2/<前缀>/<哈希>`：D1 正式引用的原始输入和派生文件，key 保存在清单中。
- `vectorize/*.ndjson`：资产 chunk 与图实体向量，可向新索引批量重建。

导出包包含账号密码哈希、MCP token 哈希、个人资料和 Agent 记忆。应放在加密磁盘或
受控备份介质中，禁止提交到 Git。默认忽略 `.cloudmind-exports/` 和
`cloudmind-export-*/`。

## 导出

在仓库根目录执行：

```powershell
pnpm data:export -- --output C:\backups\cloudmind-2026-07-24 --remote
pnpm data:validate -- --package C:\backups\cloudmind-2026-07-24
```

可以用 `--database`、`--bucket`、`--asset-index`、`--graph-index` 覆盖
`wrangler.jsonc` 的来源资源。导出目录必须尚不存在，命令不会覆盖旧备份。

导出只收录 D1 正式引用的 R2 对象。中断写入留下、尚未被 D1 绑定的对象属于孤立对象，
不会进入可恢复数据包；对应输入仍保留在 D1，工作流重试会按固定 key 恢复绑定。

## 准备恢复资源

恢复目标必须是隔离的新资源：一个空 D1、一个空 R2 bucket、两个 1024 维 cosine
Vectorize 索引。恢复命令会先对 D1 应用仓库中的全部 migration，再按外键顺序导入
NDJSON，并从 `asset_chunks` 重建 FTS。先为资产索引建立以下 string metadata 索引：

`aiVisibility`、`domain`、`sourceKind`、`sourceHost`、`collectionKey`、`type`、
`scopeId`、`recordKind`、`contextKey`、`createdAt`。

图实体索引建立 `scopeId` 和 `contextKey`。恢复命令会先检查这些索引，缺项时停止，
避免恢复后项目过滤失效。

## 恢复

```powershell
pnpm data:restore -- --package C:\backups\cloudmind-2026-07-24 --remote `
  --database cloudmind-restore-db `
  --bucket cloudmind-restore-assets `
  --asset-index cloudmind-restore-vectors `
  --graph-index cloudmind-restore-graph `
  --confirm-empty-target
```

恢复顺序固定为：离线校验全部文件、检查 Vectorize metadata、迁移 D1、导入业务表、
重建 FTS 并核对行数、上传 R2、从 NDJSON 重建两个向量索引。命令不会创建资源，也
不会删除目标数据。

恢复器会为显式目标 D1 生成临时 Wrangler 配置，完成 migrations 后自动删除。D1
业务表按外键顺序和请求字节分批导入；超长文本按 UTF-8 边界拆分后逐段拼回，避免
触发单条 SQL 长度限制。表行数核对也分批执行，以适配 D1 的 compound query 限制。

R2 或 Vectorize 阶段失败后，确认目标仍是本次隔离恢复资源，再加 `--resume` 重跑。
续跑时 D1 每张表的行数必须与清单完全一致，否则命令拒绝继续；R2 put 与 Vectorize
upsert 可重复执行。D1 导入失败时使用新的空 D1 重试，避免接着写入部分数据。

## 验收与切换

恢复完成后至少检查：

1. D1 各表行数与 `manifest.json` 一致。
2. R2 原始文件和清洗结果可读取，抽查文件 SHA-256 与清单一致。
3. 两个 Vectorize 索引数量与清单一致，三维过滤可命中预期项目。
4. 部署 Worker 到恢复资源后，执行项目隔离验收和一次软删除、恢复测试。
5. 验收通过前保持原资源不变；切换失败时把 Worker 绑定切回原资源。

数据包 v2 直接恢复导出的向量值和 metadata，并包含硬删除审计。需要切换嵌入模型时，先恢复 D1/R2，
随后通过资产重处理生成新模型向量；旧索引保留到查询验收完成后再下线。

2026-07-24 已完成一次生产只读导出到全新隔离资源的演练：D1 逐表行数、FTS 和外键
检查通过，R2 回读抽样校验通过，两个 Vectorize 数量与清单一致，项目 `contextKey`
过滤在 3 个项目上下文中通过。演练资源在记录结果后已清理，生产资源未写入。

## 硬删除

`forget` 默认执行可恢复 soft 模式。永久删除前先 soft forget，再以同一个精确
`scopeId + contextKey` 调用 `forget`，设置 `mode=hard`，并让 `confirmId` 与 `id`
完全一致。hard 会清理整个 memory 版本链；进入 `purge_pending_at` 后禁止恢复。

清理顺序固定为 R2、chunk Vectorize、图 Vectorize、D1。某阶段失败时，
`deletion_audits` 记录阶段错误码，D1 版本链保留供相同请求重试。完成后审计只保留
目标哈希、各存储清理数量和完成时间。共享 provenance 的 L2 记录不会随单条记忆删除。
