# 工程质量与发布

> 模块定位：维护严格类型、静态检查、测试、检索评估、构建和发布门禁。
>
> 对应代码：`package.json`、`CHANGELOG.md`、`.github/workflows/quality.yml`、
> `wrangler.jsonc`、`worker-configuration.d.ts`、`config/worker-secrets.json`、`scripts/*`、
> `src/features/workflows/server/*`、`tests/*`
>
> 所属 M 里程碑：[`M7 工程质量与发布`](../roadmap.md#m7-工程质量与发布)
>
> 当前状态：已完成
>
> 最近更新时间：2026-08-02

## 职责与边界

- TypeScript strict 和 Biome 负责类型、格式与静态规则。
- Vitest 覆盖核心服务、repository 边界、纯函数和回归行为。
- eval 独立检查检索各阶段，生产构建检查 HonoX 和样式产物。
- 发布流程负责版本、迁移、构建、部署与回滚说明。

## 结构与数据流

```text
source + docs
  -> typecheck -> lint -> unit/integration tests -> retrieval eval -> build
  -> CI + infrastructure checks -> version/release -> deploy -> smoke / rollback
```

## 关键决策

1. `noExplicitAny`、未使用代码、type-only import 等规则按 error 执行。
2. 核心业务逻辑必须有单测，纯视觉改动使用人工检查。
3. eval 既检查最终指标，也保留各检索阶段指标，便于定位回归。
4. 文档中的完成状态必须有测试、可运行功能、提交或人工确认支撑。
5. M7 分为开发前置门禁和发布收尾；前置门禁先保护后续数据模型与生命周期改动。
6. 密钥只通过 Cloudflare secret 或本地 `.dev.vars` 注入；配置文件只保存无值清单，
   `JWT_SECRET` 缺失时直接拒绝启动认证链路。
7. Queue 消费者使用 D1 条件更新原子认领步骤；失败消息显式重投，超过
   `max_retries` 后由 Cloudflare 投递到 DLQ。
8. 发布顺序固定为远端 migration、精确核验、Worker deploy、生产冒烟。冒烟失败时
   自动恢复发布前 Worker version。
9. D1 migration 只前进；表结构改动遵守 expand/contract，保证发布前后的 Worker
   都能使用迁移后的数据库。

## 当前实现

- `pnpm gate` 统一执行配置边界、绑定漂移、严格类型、Biome、Vitest、25 条检索
  eval、生产构建和 Workers runtime 集成测试。
- `.github/workflows/quality.yml` 在 push 与 pull request 中固定 Node、pnpm 和
  frozen lockfile，并执行同一条完整门禁。
- `wrangler types` 生成并提交 `worker-configuration.d.ts`；CI 使用 `--check`
  阻止配置和类型漂移。Vectorize 适配器只依赖实际使用的索引方法。
- `config/worker-secrets.json` 声明必需与可选密钥；检查脚本阻止密钥进入
  `wrangler.jsonc vars`，并校验 `.dev.vars`/`.env` 忽略规则和 Queue DLQ。
- workflow step 通过条件更新完成原子认领；新鲜 `running` step 的重复消息进入 retry，
  超过 30 分钟的遗留状态允许重新认领。资产本身也用条件更新保证同一时间只有一个
  workflow run 占用处理槽位。
- 生产 smoke 将全部已创建的测试资产放入 finally 清理；one-click deploy 的配置备份
  使用系统临时目录并在退出时删除，不污染仓库工作区。
- 官方 Workers Vitest 集成在 Miniflare 中应用真实 D1 migrations，并验证 D1
  原子认领、Queue 的逐条 ack/retry 行为，以及 0017 migration 后的 memory 版本
  原子切换。
- `scripts/ops/rescope-vectors.mjs` 可幂等补齐向量三维归属，并在已有值冲突时中止；
  `scripts/record-filter-acceptance.mjs` 使用现有 token 做只读生产 MCP 验收。
- 版本已提升为 `0.3.0`，`release:check` 会同时校验 Semantic Versioning 和
  `CHANGELOG.md` 的带日期版本条目，并已纳入 `pnpm gate`。
- `release:deploy` 会保存发布前 Worker version，应用远端 D1 migrations，读取
  `d1_migrations` 精确核对 19 个 migration 的名称与顺序，再发布 Worker。
- 生产冒烟覆盖公开 health、登录 HTML 和未鉴权 MCP 401。发布后冒烟失败时，脚本会
  自动回滚 Worker 并复跑冒烟；split traffic 会中止自动回滚。
- `release:rollback` 支持指定 version 手动回滚；`release:rollback:rehearse` 会切到上一
  稳定版本，冒烟后恢复开始时版本，并在异常路径再次尝试恢复。
- Cloudflare Workers Builds 的 `main` 生产 Trigger 已配置 `pnpm release:deploy` 和
  `SMOKE_BASE_URL`。首次私有部署使用 `deploy:first`，在尚无公开 URL 时跳过冒烟。
- 完整操作见[发布与回滚 Runbook](../runbooks/发布与回滚.md)。
- v0.3.0 已完成真实自动发布：Cloudflare Build 先确认 19 个 migration 全部匹配，
  再发布 Worker 并通过 health、login 和 MCP 401 冒烟。
- 生产回滚演练已从 Worker version `d79ab361` 切到 `f1c09fb8`，冒烟后恢复
  `d79ab361` 并再次通过冒烟；最终生产保持单一 version 100% 流量。

## 验证方式

提交前运行 `pnpm gate` 和 `git diff --check`。修改 `wrangler.jsonc` 后先运行
`pnpm bindings:generate` 更新生成文件；CI 会用 `pnpm bindings:check` 拒绝漂移。
Workers 集成测试使用本地 Miniflare，不需要连接真实 Cloudflare 资源。发布脚本单测
覆盖 migration 对比、稳定版本选择、split traffic 拒绝、版本元数据和生产冒烟重试。
2026-07-24 的完成证据为：`pnpm gate` 通过，Quality Gate `30104398954` 通过，
Cloudflare Workers Build `9488add2-fe3d-4326-a52a-99506a1c710c` 成功，生产回滚与
恢复后的冒烟均通过。
