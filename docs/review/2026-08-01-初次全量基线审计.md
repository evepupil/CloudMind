## Findings

### R-01 [P1] PDF finalize 会清空 `rawR2Key`（已解决）

- 位置：`src/features/workflows/server/pdf-ingest-workflow.ts:88-90`、`src/features/workflows/server/shared-workflow-steps.ts:407-435`、`src/platform/db/d1/repositories/d1-asset-repository.ts:673-770`
- 触发条件：PDF 上传成功处理，或对已有 PDF 资产执行 reprocess。
- 影响：PDF 的原始 R2 快照指针会被写成 `null`。后续恢复、导出或重处理无法通过 D1 找到原始 PDF，即使 R2 对象还存在也失去了系统入口。
- 证据：PDF workflow 的 finalize 明确配置 `getRawR2Key: () => null`。shared finalize 将回调结果用 `?? null` 处理并传给 `completeAssetProcessing`；repository 在 `rawR2Key !== undefined` 时更新字段，因此这里会主动覆盖成空值。
- 建议：PDF finalize 保留 `context.asset.rawR2Key`，或省略该字段让 repository 保持旧值；补充成功处理和 reprocess 后 `rawR2Key` 仍存在的回归测试。
- 处理：PDF workflow 将快照 key 带入 finalize state，成功处理和 reprocess 均保留 `rawR2Key`。

### R-02 [P1] running step 重投时被 ack，workflow 可能永久卡死（已解决）

- 位置：`src/platform/db/d1/repositories/d1-workflow-repository.ts:273-294`、`src/features/workflows/server/runtime.ts:299-309`、`src/features/workflows/server/queue-batch-consumer.ts:4-13`
- 触发条件：Worker 在 step 被标记为 `running` 后、step 完成或失败前崩溃、超时，随后 Queue 重投同一消息。
- 影响：`markWorkflowStepRunning` 只允许 `pending/failed` 认领。重投看到 `running` 时 runtime 静默返回，batch consumer 因为没有异常而 ack 消息；step 没有机会回到 `pending/failed`，资产可能永久停在 `processing`。
- 证据：当前实现没有 stale `running` 的超时回收或重新认领逻辑。
- 建议：增加运行超时和回收机制，或让未认领的消息进入可重试路径；补充“step 已 running 后 worker 崩溃、消息重投并最终完成”的测试。
- 处理：重复消息在新鲜 `running` 状态下抛错进入 Queue retry；运行超过 30 分钟后允许重新认领，并增加集成回归测试。

### R-04 [P1] restore 失败回滚不清理 L2 图谱和 graph vectors（已解决）

- 位置：`src/features/memory/server/lifecycle-service.ts:277-308`、`src/features/workflows/server/shared-workflow-steps.ts:441-550`、`src/features/workflows/server/runtime.ts:265-420`
- 触发条件：`restore_memory` 恢复资产后重新处理，workflow 在 `extract_entities` 写入实体、statement、edge 或 graph vector 后的后续步骤失败。
- 影响：资产会被重新 soft-delete，asset chunk vectors 会尝试清理，但 L2 D1 记录、entity vector 和 graph vector 仍可能存在。后续图召回、再次恢复和一致性修复可能读到已回滚资产的图谱副作用。
- 证据：restore 回滚只调用 asset vector store 的 `deleteByIds`；图谱写入在 workflow 的 `extract_entities` 中调用 `writeGraphToMemory`、`graphVectorStore.upsert` 和 `setEntityVectorId`；runtime 的失败处理只有 workflow/asset 状态标记，没有图谱补偿清理。
- 建议：为图谱写入增加可回滚或可幂等的补偿步骤；补充在图谱写入后注入失败，并断言 D1 L2 记录与 graph vectors 均被清理的测试。
- 处理：图谱写入补齐 entity provenance；restore 失败按恢复时间反查本次产生的 statement/edge/entity，先清理 graph vectors，再删除无其他来源的 L2 记录，保留共享来源，并增加单测和 Workers 集成测试。

### R-05 [P1] hard delete 失败后 `purge_pending_at` 会锁死记录（已拍板不改）

- 位置：`src/platform/db/d1/repositories/d1-memory-purge-repository.ts:206-239,290-301`、`src/features/memory/server/lifecycle-service.ts:263-267,337-385`
- 触发条件：`prepareMemoryPurge` 已将资产标记为 `purge_pending_at`，随后 R2、asset vectors、graph vectors 或最终 D1 删除任一步失败。
- 影响：失败处理只把 deletion audit 标成 failed，不会清理 `purge_pending_at`，也没有补偿已经完成的外部删除。restore 又明确拒绝 purge-pending 记录，导致“还没删完、也不能恢复”的锁死状态。
- 证据：`prepareMemoryPurge` 先写 pending 标记；`failMemoryPurge` 只更新 `deletion_audits`；restore 在看到 `purgePendingAt` 时直接抛出 `PURGE_PENDING`。
- 建议：将 hard delete 改为可续跑的阶段流程，或定义明确的失败回滚策略；至少让未开始实际删除的失败可以清理 pending 标记，并补充各阶段失败后的恢复/续跑测试。
- 复核结论：不改。hard delete 失败后可再次执行 `prepareMemoryPurge` 创建新审计并重试；pending 状态有意阻止 restore，防止未完成删除期间恢复数据，当前没有确认的锁死 bug。

### R-12 [P1] 生产 smoke 只清理三条测试资产中的一条（已解决）

### R-14 [P1] MCP bearer token 长期明文存储并反复输出

- 位置：`src/platform/db/d1/schema/mcp-tokens.ts:3-20`、`src/platform/db/d1/repositories/d1-mcp-token-repository.ts:10-75`、`src/features/mcp-tokens/server/service.ts:25-35`、`src/features/mcp-tokens/components/mcp-tokens-page.tsx:150-174`
- 触发条件：创建 MCP token、打开 `/mcp-tokens` 页面、读取 D1 导出或读取页面中的安装内容。
- 影响：token 是可直接复用的 bearer credential。当前 D1 同时保存 `tokenValue` 和 hash，列表服务读回完整值，页面还把完整 token 放入 DOM、安装 prompt 和配置 JSON。数据库快照、浏览器页面、截图、日志或复制内容一旦泄露，攻击者可以直接调用 MCP。
- 建议：持久层只保留 hash，明文只在创建成功时展示一次；若产品必须再次展示，应采用受控加密存储并限制输出范围。补充 token 泄露面和创建后展示策略的测试。

### R-03 [P2] 同一资产可以并发创建多个 workflow run（已解决）

- 位置：`src/features/workflows/server/runtime.ts:161-196`、`src/platform/db/d1/repositories/d1-workflow-repository.ts:90-105`、`src/features/ingest/server/service.ts:482-503`
- 触发条件：资产处于 `processing` 时再次调用 reprocess 或重复触发 ingest。
- 影响：`enqueueWorkflow` 只对 `ready` 和 `failed` 做短路，`processing` 仍会新建 run。多个 run 可以同时调用 AI、写 chunks/vector、更新 summary，最终写入顺序不确定。
- 建议：对同一资产建立 active run 门闩或唯一约束；重复触发时复用已有 run 或返回明确的冲突结果；补并发触发测试。
- 处理：资产状态使用 `pending/ready/failed -> processing` 条件更新原子认领，竞争调用直接复用当前资产状态，并增加并发认领测试。

### R-06 [P2] Web 图谱/时间线/整合视图缺少 `contextKey`（已解决）

- 位置：`src/features/memory/server/routes.ts:27-39`、`src/features/memory/server/memory-browse-service.ts:17-103`
- 触发条件：同一 personal scope 下存在多个 project context，用户访问 `/api/memory/graph`、`/api/memory/timeline` 或 `/api/memory/consolidation`。
- 影响：路由不读取或传递 `contextKey`，browse service 只按 `PERSONAL_SCOPE` 查询。不同项目的记忆会混合展示，与 Search/MCP 的项目过滤语义不一致。
- 建议：给 browse service 和路由增加 context 过滤，明确默认 context 的来源；补同一 scope 下两个项目互不串出的测试。
- 处理：SSR 和 `/api/memory/*` 路由统一校验并传入可选 `contextKey`，browse repository 查询同步使用该过滤条件，并增加路由回归测试。

### R-07 [P2] 图谱 ANN 种子阶段没有按 `recordKind` 过滤

- 位置：`src/features/memory/server/graph-recall.ts:64-89`、`src/platform/db/d1/repositories/d1-memory-repository.ts:372-396`、`src/features/workflows/server/shared-workflow-steps.ts:554-565`
- 触发条件：图向量索引同时存在 `library` 和 `memory` 数据，调用 Search/Ask/recall 时传入 `recordKinds`，且错误 record kind 的向量占据 seedTopK。
- 影响：graph seed filter 只下推 `scopeId` 和 `contextKey`，graph vector metadata 也没有 `recordKind`。D1 后续反查实体和 statement/edge 时才部分应用 record kind；错误种子可能提前占满 ANN 名额，允许范围内的实体无法进入 BFS，图证据会静默减少。
- 建议：明确实体跨 record kind 的共享语义；若 record kind 需要参与图召回，就在 graph vector metadata 和 seed filter 中补齐，或扩大种子候选后再做严格过滤；补混合 record kind 回归测试。

### R-08 [P2] 中文 summary-only 评分与 Ask 的 tokenization 不一致（已解决）

- 位置：`src/features/search/server/summary-scoring.ts:11-19,27-61`、`src/features/chat/server/service.ts:195-217,253-307`
- 触发条件：中文查询连续书写、没有空格，且相关资产主要依赖 summary-only evidence。
- 影响：summary 评分按空格/标点切分并要求词长至少 2；Ask 的覆盖判断则对连续中文按双字切分。Search 可能低估 summary-only 资产，Ask 复用 Search 结果后会少拿到本应进入 grounding 的中文证据。
- 建议：两条链路共用 CJK-aware token helper；补不带空格的中文 summary-only 查询回归测试。
- 处理：新增共享 mixed-text tokenizer，summary scoring 与 Ask 覆盖率判断共用 CJK 双字切分，并增加连续中文查询测试。

### R-11 [P2] boosted navigation 的最终 URL 与页面内容可能不一致（已解决）

- 位置：`public/boost.js:77-118,147-170`
- 触发条件：boosted 同源链接发生重定向，例如未登录访问受保护页面并被重定向到登录页。
- 影响：`fetchPage` 已读取 `response.url`，但只返回 HTML；`navigate` 和 `swap` 仍用原始 URL 执行 `pushState`。地址栏可能显示原受保护页面，页面内容却是登录页，刷新、回退和收藏行为会混乱。
- 建议：让 fetch 返回 HTML 与最终 URL，pushState 使用最终落点；补 302 到登录页的导航回归测试。
- 处理：boosted fetch 返回最终响应 URL，导航和 history state 均使用重定向后的最终地址。
